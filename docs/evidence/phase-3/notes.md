# Phase 3 evidence — 2026-11-03 (Asia/Dhaka)

The same 50 state tests run on PGlite and PostgreSQL. The default suite also retains all 99 prior tests. Native PostgreSQL 16.11 was already installed locally; the harness creates a fresh database cluster under ignored `.data`, binds only to 127.0.0.1 on an ephemeral port, uses synthetic trust-authenticated fixtures without a password, and removes the cluster after the tests. `pg` 8.23.1 and its types are development-only dependencies. No existing database, service credentials or `DATABASE_URL` are used by native tests.

PGlite uses one connection and serializes transactions, so its concurrent-call tests cannot establish independent lock contention. Native tests use a 20-connection pool with a 32-connection server. Seven cases explicitly inspect `pg_stat_activity.wait_event_type='Lock'` before releasing a held lock: six action-at-publication cases and one cache-reference-versus-purge case. The production PGlite/Neon and native test bridges execute the same Drizzle SQL through the same query functions; no correctness is implemented in the bridge.

## Matrices and boundaries

- **T16:** 6 actions × 3 timings = 18 matrix cases per backend, 36 combined. Actions: cancel the same transcript, retry, edit, delete, stall fence, second start. Timings: before delayed claim, during stage work, action holds the project lock while publication waits. Retry fixtures first establish the required terminal job; stall fixtures establish a prior claim whose heartbeat becomes stale. Every action increments the epoch exactly once; the old job is fenced; at most one queued/running job remains. The 15 non-delete matrix cases per backend also verify duplicate winning publication. Additional cases cover 12 identical concurrent starts, competing edit CAS and cross-job artifact-fingerprint reuse.
- **T19:** post-commit/pre-start interruption, lost run ID, 12 competing duplicate claims, heartbeat stopping and a five-attempt dispatch ceiling. A replay of the winning claim is idempotent; a foreign claim does no work. Local adapter recovery acknowledges the existing winner without giving a duplicate authority.
- **T20 / T13:** five settlement modes (usage, incomplete-with-usage, timeout, orphan crash, provably never sent); 30 independent jobs concurrently reserve against two 10,000-micro budgets. Exactly five 2,000-micro reservations fit. Both ledgers are checked after each returned reservation. Three ordinary attempts plus one repair are the maximum; settlement is idempotent and actuals are capped at the upper bound. Original-day settlement across Dhaka midnight and the 80-percent Terra signal are checked. A one-cent cap rejects a 20,000-micro attempt, marks that job failed and keeps a previously saved artifact readable. Reasoning tokens are already included in output usage and are not charged twice.
- **Owner quotas:** five simultaneous fresh-project admissions admit three; deleting projects cannot erase the durable count. Twenty simultaneous one-segment replan requests admit ten. New Dhaka days have separate quota rows.
- **T21:** 60 callers initialize 15,728,640-byte media across 60 projects against 800,000,000 bytes. Exactly 50 fit (786,432,000 pending bytes). Smaller finalize, duplicate finalize, abandoned reservations, rejected uploads, interrupted physical cleanup, actual committed bytes, anchors and pinned media are checked. Concurrent transfer admission is gated, pinned requests bypass that gate, and the month counter resets once under its row lock. Seven abandoned objects demonstrate the opportunistic maximum of five; a 107-object daily backlog drains fully. Ready source videos expire after 72 hours; pinned media survives.
- **T24:** four interruptions per backend: Blob removal 1, 2, 3 and before final SQL commit. Fixtures contain media, an anchor, a stray prefixed object, transcript, segments, job, track, review, stage attempts, shared/exclusive cache references and a spend reservation. Failed cleanup leaves the ledger charged and the project fenced. Reconciliation finishes cleanup, preserves the shared result and spend history, removes exclusive content and child rows, releases bytes once, and makes rerun a no-op. Sharing is revoked and project/track/media visibility queries return null immediately; HTTP 404 mapping belongs to Phase 4. Additional cases cover a late upload, a new concurrent shared reference and 30-day orphan cache retention.
- **Lease fences:** a second owner cannot claim a live lease. After expiry, the lease epoch increases and the stale holder cannot reserve, settle, write stage output, publish or release the new lease. Its orphan reservation becomes conservatively spent through reconciliation.

## Schema and cleanup details

Two additive migrations introduce owner quota and anchor reservation journals, a transfer-month marker and a media charge state. These are absent from the proposed C.2 SQL but necessary to make the specified accounting persistent and idempotent. The catalog test independently applies the original C.2 SQL plus the handwritten extension fixture and compares all columns, defaults, enums, checks, primary/unique/FK constraints and partial indexes. No original constraint was removed. The prior dispatch fixture now includes a valid active-job/transcript authority pointer; its existing assertions are retained.

The deletion fence is immediate; physical purge waits out issued upload reservations (10-minute token plus 5-minute grace). All Blob removals precede the final transaction that releases storage and deletes the project. A crash leaves enough rows to retry. Media charge state distinguishes pending, committed and already released bytes without altering the recorded actual file size. Cache writers and purge lock cache rows before updating references, so a concurrently added reference cannot be cascaded away accidentally.

`reconcile` returns exactly `redispatched`, `fenced`, `reservationsConverted`, `storageReleased` and `purged`. StorageReleased counts released objects; purged counts completed project purges. Opportunistic storage/orphan batches are at most five. Daily mode drains storage/orphan backlogs and paginates deleting projects, including projects waiting for upload leases. Failures are reported with generic structured codes and IDs, never caption text or credentials.
